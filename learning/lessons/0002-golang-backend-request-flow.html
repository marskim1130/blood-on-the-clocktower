Go 后端第一课：一条 WebSocket 命令

目标：能从前端一次“投票/开始游戏/加入房间”出发，读懂它如何经过 Go 服务端，并知道应该在哪一层排查问题。

先看执行链

前端 GameWebSocketClient
  -> WebSocket /ws
  -> ws.Hub.HandleWebSocket
  -> handleMessageV2 / handleCommandV2
  -> session.AuthoritativeGameSession.ExecuteObserved
  -> gameplay.GameSession.Apply
  -> sessionstore.Replace
  -> gameplay.ProjectionFor(playerID)
  -> ordered outbound queue
  -> 每个玩家收到自己的 RoomState

这就是后端的“请求进入、业务提交、响应出去”。读代码时先沿这条线走，不要从某个角色能力文件开始猜。

Go 语法在项目中的对应物

Go 概念项目例子你要记住什么
包 [package]internal/ws、internal/session按职责组织代码；小写名称不导出，大写名称可被别的包使用。
结构体 [struct]session.Actor、session.Command把一组数据组成明确的输入对象。
方法 [method](s *AuthoritativeGameSession) Execute(...)方法接收者通常是业务对象本身。
接口 [interface]session.Engine、RoomRecordStore调用方只依赖行为；内存、文件、Redis 可以替换实现。
错误值 [error]ErrInvalidCredential、errors.Is错误是返回值，不靠异常跳转；上层再映射成稳定协议错误码。
并发原语 [concurrency primitives]sync.Mutex、atomic.Pointer、go sender.run()锁保护共享状态；后台 goroutine 专门按顺序发送消息。

最重要的后端边界

1. Hub 是适配器 [adapter]

internal/ws/hub_v2.go 把 JSON 的 ClientMessage 翻译成 Go 命令。它负责协议版本、活动连接、错误码和投递，不应该自己保存一份房间状态。

2. AuthoritativeGameSession 是唯一权威 [single authority]

ExecuteObserved 先拿房间锁，再复制当前记录和游戏引擎，验证凭证、权限和 clientSequence，应用候选变化，持久化成功后才替换 committed 视图。

current := s.committed.Load()
candidate := cloneRecord(current.record)
engine := current.engine.Clone()
// 校验并修改 candidate / engine
if err := s.store.Replace(ctx, current.record.RoomRevision, data); err != nil {
    return CommandResult{}, err
}
s.committed.Store(&committedView{record: candidate, engine: engine})
核心不变量 [invariant]：持久化失败时，内存中的已提交状态不前进；广播只发生在提交之后。这样客户端不会看到“服务器重启后消失”的成功状态。

3. Gameplay 只管规则

internal/gameplay 不知道凭证、WebSocket 或 Redis。GameSession.Apply 接收类型明确的命令，例如 CastVoteCmd、StartGameCmd，然后校验当前阶段、角色和胜负条件。

4. Projection 是隐私边界 [privacy boundary]

ProjectionFor(recipientID) 为每个接收者生成完整但不同的视图：说书人可以看到角色和夜间管理信息，普通玩家看不到其他人的身份。后端不能把完整游戏对象直接广播给所有人。

一次“投票”如何定位问题

  1. 客户端没有发出：看 room-session-store.ts 和 Core 客户端。
  2. 服务端报 INVALID_MESSAGE：看 HandleWebSocket 的 JSON/协议版本校验。
  3. 报 STALE_CONNECTION：看活动连接接管和连接代数。
  4. 报 UNEXPECTED_SEQUENCE：看客户端持有的下一个序号，或请求完整房间状态。
  5. 报 INVALID_COMMAND：看 toGameCommand 和 GameSession.Apply。
  6. 服务端返回成功但其他玩家没更新：看提交后的投影生成和有序出站队列。
